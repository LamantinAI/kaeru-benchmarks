| Problem | Options | Tradeoff |
|---|---|---|
| Typo tolerance | Offer “did you mean”; retry with fuzzy matching when exact results are sparse; always include fuzzy matches | Suggestions give users control. Fallback limits noise. Always-on matching improves recall but can return unrelated results. |
| Ordering | Explicit match tiers; relevance scoring in an existing search backend | Match tiers are predictable: exact title → phrase → token → fuzzy. Backend scoring offers more flexibility but needs tuning. |
| Filter reset | URL parameters; session storage; local storage; account preferences | URL state supports sharing/bookmarks. Session storage lasts within a tab. Local storage persists across visits. Account preferences require server work. |

Fuzzy matching commonly uses bounded edit distance; expansion limits matter for performance. Elasticsearch documents these controls, but there’s no evidence this project uses Elasticsearch. [Fuzzy-query documentation](https://www.elastic.co/docs/reference/query-languages/query-dsl/query-dsl-fuzzy-query)

For filters, browser storage has different lifetimes: session storage is scoped to a tab, while local storage persists across browser restarts. [MDN storage documentation](https://developer.mozilla.org/en-US/docs/Web/API/Web_Storage_API) URL parameters provide another place to encode the selected state. [MDN URL documentation](https://developer.mozilla.org/en-US/docs/Web/API/URL/searchParams)

My provisional preference is **conservative fuzzy fallback, explicit relevance tiers with a stable ID tie-breaker, and URL-based filter state**. That’s a proposal, not an implementation decision. Keep structured filters exact even when text search becomes fuzzy.

Before selecting an approach, the missing evidence is the actual search backend, representative queries with expected rankings, dataset size, and the browser reload flow. Evaluation should cover typo recovery, irrelevant matches, ranking quality, latency, and refresh/back/reset behavior.
