[The service](/workspace/search/service.py:4) preserves incoming result order—it doesn’t explicitly sort by ID. There’s no query matcher or browser code here, so typo handling and the reload reset couldn’t be reproduced.

| Problem | Options | Main tradeoff |
|---|---|---|
| Typo tolerance | Bounded edit-distance matching in the application; database similarity search; dedicated search engine | Application matching avoids infrastructure but needs performance and accuracy checks. PostgreSQL offers indexed [trigram similarity](https://www.postgresql.org/docs/18/pgtrgm.html); Elasticsearch offers [fuzzy matching](https://www.elastic.co/guide/en/elasticsearch/reference/current/query-dsl-fuzzy-query.html). Neither backend is established by this workspace. |
| Ordering | Simple relevance rules; database text ranking; engine scoring | Explicit rules are easier to explain; richer ranking needs representative queries and tuning. PostgreSQL supports [weighted text ranking](https://www.postgresql.org/docs/current/textsearch-controls.html). |
| Filter reset | URL parameters; session storage; local storage; account-saved preferences | URLs make searches bookmarkable and shareable. [Session storage](https://developer.mozilla.org/en-US/docs/Web/API/Window/sessionStorage) survives reload within a tab; [local storage](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage) persists across browser sessions. Account preferences require server-side work. |

My provisional preference is:

- **Typos:** conservative fuzzy fallback when exact matches are insufficient, with stricter handling for short words and identifiers.
- **Ordering:** exact matches first, then token/prefix matches, then fuzzy matches; use ID only to break ties. Rank before pagination.
- **Filters:** use [URL parameters](https://developer.mozilla.org/en-US/docs/Web/API/URLSearchParams) as the authoritative state, restoring them before the first search request. Choose storage instead if filters should be private to the browser.

Before selecting an approach, the missing evidence is the actual backend, dataset size, representative failed queries, and frontend state lifecycle. Those determine whether a small application change is sufficient.

Existing project constraints also matter: no new dependencies this sprint, additive API changes, and service-owner review before merging search-service changes. Memory records the owner as away for two weeks. No implementation option has been adopted.
